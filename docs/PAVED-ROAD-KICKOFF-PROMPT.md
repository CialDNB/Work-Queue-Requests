## Mission

Team members across CIAL increasingly build internal mini-apps — Arena, Arena Go for sales, Atlas, and others — on whatever platform is at hand: lovable, railway, v0, base44. The builder energy is an asset; the security, cost, and maintenance exposure is not (real example from our own portfolio: the original Atlas shipped real employee names and ILS salaries embedded in a static HTML seed). Meanwhile the Cloudflare + GitHub model has proven itself across four in-flight projects (docshub, Arena 2.0, the Atlas rebuild, the Intercom→Linear sync): we already pay for Cloudflare Enterprise so the marginal cost of low-volume internal apps is near zero, and these apps deliberately stay OUT of the internal AWS environment.

The product of this session: a **template repo a semi-technical employee can instantiate and then just talk to Claude Code** — and everything that comes out runs on approved services with auth, RBAC, CI/CD, tests, Linear tracking, go-live gates, uptime monitoring, and docs already in place. The paved road makes the right way the easy way: nobody has to remember to add auth or tests, because the kit makes their absence impossible.

Deliverables (the repo is the product; the three outputs wrap it):
- **Output #0 — the skeleton repo itself**, built, verified, pushed (scope confirmed in D1).
- **Output #1 — GUIDEBOOK.md**: the plain-language guide for the semi-technical builder.
- **Output #2 — a leadership-level presentation on docshub**: why the paved road, what's in the box, governance, cost.
- **Output #3 — docs/IMPLEMENTATION-HANDBOOK.md**: the in-depth spec for whoever (human or agent) builds, provisions, and maintains the kit.

Each output has a distinct audience — builder, exec, maintainer — and they must not blur. Every claim in #1 and #2 must be true of the repo as actually built; anything deferred (Entra app registration, zone email DNS) is marked "pending setup" with its Linear issue, never described as live.

## What the skeleton repo must contain (build spec — adjust with written rationale, don't silently drop)

1. **Scaffold:** TypeScript Cloudflare Worker (Hono) in `src/`; Vite + React + TS SPA in `web/` served via Workers Static Assets; `wrangler.jsonc` + staging + test variants; smart placement; observability on. **Staging is the default posture for every kit app** — `staging-<app>.cialdnb.ai`, auto-deployed by CI — set up by `/new-app` without asking. Not every app warrants one: propose a skip rubric (e.g. read-only throwaway tools touching no real user data), and any skip is recorded with its reason in the app's DECISIONS.md and surfaced on the go-live checklist.
2. **Auth module (pre-built, protected core):** passwordless magic links (email behind a transport seam), KV sessions with `__Host-` cookies, Entra SSO ready behind the interchangeable-auth seam (config + redirect URI is all a new app adds), fail-closed everywhere, invite-only user allowlist, RBAC with roles (owner/admin/member/viewer baseline) + groups, per-action permission checks, append-only audit log, 404-uniformity as an invariant. Permission-matrix tests included and passing.
3. **Data layer:** D1 as system of record; starter migrations for users/sessions/groups/roles/audit plus a clearly marked place for app tables; repository pattern fencing all DB access into `src/data/` (semgrep rule enforces); R2 and KV binding templates commented and ready; daily cron for backup (D1 export to R2) + heartbeat, à la docshub `src/cron/`.
4. **API conventions (defined once, enforced by the paved road):** every kit app's API must look the same, so an agent or human moving between apps never relearns the basics. Ship `docs/API-CONVENTIONS.md`, derived from docshub/arena practice, and make the golden example + `/add-endpoint` skill embody it so deviation takes effort. Cover at minimum: URL shape and resource naming (`/api/<resource>`, casing/plural rules); one canonical JSON success/error envelope with machine-readable error codes (and never stack traces or internals in prod responses); typed request validation at the route boundary; the auth surfaces (session cookie for the SPA, Bearer `t_*` tokens for programmatic/MCP access); pagination, filtering, and sorting conventions; idempotency expectations for mutations; audit-on-write; 404-uniformity (already an invariant); and a versioning stance for internal apps (recommend additive-only changes, no version prefix until a real break forces one — but make the call and write it down).
5. **Naming conventions & resource attributability:** the Cial Cloudflare account is shared across business lines — every resource must be attributable to its app at a glance, no tribal knowledge. Define one scheme and have `scripts/provision` apply it automatically so builders can't deviate: Workers `<app>` / `<app>-staging`; D1 `<app>-db` / `<app>-db-staging`; KV `<app>-sessions`, `<app>-cache`; R2 `<app>-media`, `<app>-backups`; queues, crons, AI Gateway, and Secrets Store entries `<app>`-prefixed the same way; DNS per the domain convention; GitHub repos `CialDNB/<app>` (kebab-case); Linear projects and docshub decks carrying the app name. The counterpart rule: **binding names inside code stay uniform across all kit apps** (fix a canonical set — e.g. `DB`, `SESSIONS`, `MEDIA`, `BACKUPS`, `EMAIL`, `AI`) so everyone knows exactly what `env.DB` is in any kit app; the app prefix lives in the resource name, never the binding. Each app maintains a `docs/RESOURCES.md` manifest (resource → name → ID → purpose), generated/updated by `scripts/provision`, covering also what wrangler.jsonc can't show — DNS records, scoped tokens, AI Gateway config, Entra redirect URIs — so orphan-resource audits of the shared account become trivial.
6. **CI/CD (GitHub Actions):** biome as a HARD gate, typecheck, vitest via `@cloudflare/vitest-pool-workers` with a coverage floor that only ratchets up, gitleaks, actionlint, semgrep; auto-deploy staging on main with `/_health` smoke check; production deploy manual with build-version var; tiered pre-commit hook; CODEOWNERS on the protected core; CI never calls the AI gateway.
7. **The harness/context layer (this is the heart of the kit):** `CLAUDE.md` with prime directives adapted for internal apps, iron laws, never-do list, parallel-session etiquette, and the Linear standing rule; `docs/DECISIONS.md` seeded append-only newest-first; a learnings-capture norm; `.claude/settings.json` with the format-on-edit PostToolUse hook, a PreToolUse destructive-command guard (`rm -rf`, force-push, `reset --hard`, `DROP`/`TRUNCATE`), and protected-core scope-locking.
8. **Skills (the virtual team, run as commands):** `/new-app` (the conversational bootstrap: rename/rebrand, ask where the Linear project goes and create it with the standing rule in the description, walk the provisioning checklist applying the naming scheme, staging by default per the rubric, first staging deploy), `/add-page`, `/add-endpoint` (with a golden example route showing validation, permission check, audit, 404-uniformity, tests — the API conventions made executable), `/add-job` (cron), `/security-review`, `/qa` (drive the staging deploy in a real browser), `/ship` (PR + gates), `/go-live` (the gated checklist).
